# 请求链路与资源诊断

后台“任务 → 请求链路与邮件”列出最近请求，可按日志中的请求编号查询。每条请求关联数据库查询、只读地点服务、地图及模型请求；每段保留父段编号、开始偏移、耗时、错误状态。响应头为 `X-Request-Id` 和 `X-Trace-Id`。

默认本机或服务器 PostgreSQL 持久化，不上传到外部监控平台。只存 Express 路由模板、方法、状态、组件名、数据库操作类型和耗时。不存具体 URL、SQL 文本或参数、Cookie、API Key、对话、问卷或用户地点正文。游客也只有必要的性能/错误记录，不含个人身份轨迹。

每请求最多63个子段，另有根标识。待写队列默认128请求，每2秒最多写16条；过载或写入失败有明确计数。关闭时尽力写完；进程崩溃可能损失尚未落盘的诊断，不能代替审计日志。记录保留7天，随批次有界清理。长请求结束前，记录尚不可见；已结束请求中的未完成子任务单列 `incompleteSpans`。

RSS、堆起止值和子段边界采样最大 RSS 都是**整个进程**的读数，不是该请求的专属分配，也不等于连续观测峰值。供应商内部服务器的细节无法从本系统追踪。不要凭某条链路单独断言泄漏原因。

已评估 [OpenTelemetry JavaScript](https://opentelemetry.io/docs/languages/js/)。首版使用 Node AsyncLocalStorage 的应用内追踪及128位 Trace ID，覆盖现有数据库与公共供应商适配层；**未安装 OpenTelemetry SDK，也未声称实现完整 OTLP 导出或跨系统自动插桩**。需要连接现有 Collector 时再显式配置、评估依赖和出口；当前服务不要求第三方监控账号。

接口：`GET /api/admin/traces?offset=0&requestId=<可选UUID>`、`GET /api/admin/traces/:requestId`，均需 `system.read` 后台权限。普通账号和未登录访问会拒绝。诊断写入通过原始数据库通道，避免追踪自己形成递归。
